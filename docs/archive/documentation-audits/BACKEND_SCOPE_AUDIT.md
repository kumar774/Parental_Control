# BACKEND-ONLY SCOPE AUDIT & RESPONSIBILITY MATRIX (`BACKEND_SCOPE_AUDIT.md`)

> **Project Stage:** Phase 1 — Backend Engineering Focus
> **Target Inventory:** All 183 Canonical Parental Control Features from `Feature.md`
> **Document Purpose:** Explicitly delineates Server/Backend responsibilities from future Parent and Child Android App client implementations.
> **Date:** November 13, 2026

---

## 1. Project Scope Confirmation

> [!IMPORTANT]
> **CRITICAL ARCHITECTURAL DIRECTIVE:**
> We are currently engineering **ONLY THE BACKEND & ADMIN PLATFORM** for the Parental Control System.
> The Parent Android App and Child Android App will be designed and built in separate future phases.
> All database schemas, API contracts, WebSocket protocols, security controls, and background workers must focus strictly on server-side duties.
> Android-specific hardware and OS APIs (Camera2, Accessibility Services, DevicePolicyManager, WindowManager overlays, BroadcastReceivers) are **client runtime enforcement responsibilities**, NOT backend responsibilities.

---

## 2. Executive Scope Breakdown

A rigorous responsibility audit across all **183 canonical features** establishes:
- **Backend Required (`YES`):** **85 features** (46.4%)
  - Features requiring dedicated database tables, REST endpoints, WebSocket signaling, S3 media storage, background queue processing, or billing engines.
- **Backend Partial (`PARTIAL`):** **82 features** (44.8%)
  - Features where runtime enforcement happens on the Android device, but the backend stores configuration in `device_policies` JSONB, gates access via plan entitlements (`plan_features`), and synchronizes rules via `/api/v1/devices/:id/policy`.
- **Backend Not Required (`NO`):** **16 features** (8.7%)
  - Pure local on-device runtime mechanisms, internal helper binaries, and offline algorithms (e.g. Accessibility auto-clicker gestures, hardware volume key interception, dialer secret code intents, offline RSA/TOTP verification).
- **Total Accounted Features:** **183** (100.0% of inventory accounted for exactly once).

### Scope Distribution Summary Table:
| Scope Tier | Feature Count | Percentage | Primary Backend Deliverables |
| :--- | :---: | :---: | :--- |
| **Backend Required (YES)** | **85** | 46.4% | Auth JWTs, Device Pairing, Telemetry Timescale/PostGIS tables, Media S3 Storage, Realtime Signaling Hub, Command Queue, Stripe/Google Play Billing, Safety Alarms. |
| **Backend Partial (PARTIAL)** | **82** | 44.8% | Dynamic Policy Schema (`device_policies` JSONB), Plan Entitlements (`plan_features`), Admin Feature Flags (`system_features`), Policy Sync Endpoints. |
| **Backend Not Required (NO)** | **16** | 8.7% | Zero server compute or custom endpoints. Handled 100% locally on Android OS; backend only provides global feature kill-switch toggle in `system_features`. |
| **TOTAL** | **183** | **100.0%** | **Consolidated Canonical Feature Matrix** |

## 3. Core Architectural Distinction: Feature vs Backend Responsibility

To prevent over-engineering and architectural misattribution, the table below illustrates the precise separation of concerns for representative capabilities:

| Operational Capability | Parent Android App Responsibility | Child Android App Responsibility | Backend / Server Responsibility |
| :--- | :--- | :--- | :--- |
| **Remote Camera Photograph** (`remote_snapshot_camera`) | Renders 'Capture Photo' button; views uploaded JPEG; receives push notification upon completion. | Wakes camera sensor silently via Camera2; captures still image; uploads binary payload to presigned S3 URL. | Validates parent JWT & quota; creates `device_commands` job; issues presigned S3 upload URL; indexes `media_assets`; pushes completion event. |
| **Live Screen Mirroring** (`live_screen_mirror`) | Requests live mirror session; displays WebRTC video viewport; toggles audio/video controls. | Captures display via `MediaProjection`; encodes H.264/VP8 video; establishes P2P WebRTC peer connection. | Authenticates active Pro/VIP plan & minutes quota in Redis; coordinates SDP offer/answer signaling via WebSocket; provisions STUN/TURN relays. |
| **App Blocking** (`app_blocking`) | Parent configures app limits / blacklists in UI; views usage charts. | Accessibility & UsageStats watcher intercepts blocked package launch; shows overlay block screen. | Stores app rules in `device_policies.rules`; increments `policy_version`; dispatches `policy.updated` push; logs rule audit trail. |
| **Geofencing & Safe Zones** (`geofencing`) | Draws geofence circle/polygon on map; defines arrival/departure alert triggers. | Fused GPS service polls location; submits coordinates to `/api/v1/child/telemetry/location`. | Stores PostGIS spatial boundary; executes point-in-polygon queries; detects entry/exit/dwell events; triggers push alert to parent. |
| **Emergency Lock** (`instant_device_lock`) | Taps 'Lock Device Now' dashboard button. | Device Admin receiver executes `DevicePolicyManager.lockNow()`; displays emergency unlock screen. | Authenticates parent; writes `device_commands` with high priority; dispatches immediate WebSocket/FCM push; logs execution state. |
| **Hardware Key Interception** (`hardware_key_interception`) | None (Transparent background security mechanism). | Accessibility service intercepts `flagRequestFilterKeyEvents` and consumes volume/power keys to block bypass. | None. Pure on-device OS event interception. Governed only by global kill-switch flag in `system_features`. |

## 5. Shared End-to-End Workflows

The Parental Control system operates via 5 core end-to-end communication pipelines:

### Pipeline 1: Policy Sync Flow (Parent App → Backend → Child App)
1. **Parent Configuration:** Parent updates rules (e.g. Bedtime Schedule, Web Filter VPN, Block YouTube) in Parent App UI.
2. **Backend Validation:** Backend verifies parent JWT, validates schema, writes to `device_policies.rules`, increments `policy_version`, and publishes a Redis Pub/Sub event.
3. **Push Dispatch:** Backend sends a lightweight silent push (`{ action: 'policy_update', version: 14 }`) over persistent WebSocket or Firebase Cloud Messaging (FCM).
4. **Child Synchronization:** Child App calls `GET /api/v1/child/policy?version=13`. Backend returns HTTP 200 with new rules JSON. Child app applies rules locally to DevicePolicyManager, VPN, and Accessibility engines.

### Pipeline 2: Remote Capture Flow (One-Shot Camera / Screen Snapshot)
1. **Parent Trigger:** Parent taps 'Capture Photo' in Parent App.
2. **Backend Command Queue:** Backend validates parent quota in Redis (`quota:{parent_id}:snapshots`), creates a pending row in `device_commands`, and dispatches `command.exec` to Child device via WebSocket.
3. **Child Execution:** Child daemon wakes camera sensor silently, captures JPEG, and requests an authorized S3 upload URL via `POST /api/v1/child/media/upload-url`.
4. **S3 Ingestion & Indexing:** Child uploads directly to MinIO/S3 using the presigned URL. Backend indexes the file in `media_assets` and pushes a `media.ready` notification to the Parent App.

### Pipeline 3: Realtime WebRTC Live Monitoring Flow
1. **Session Authorization:** Parent requests live screen or camera session. Backend checks active subscription plan and increments minute quota counter in Redis.
2. **Signaling Hub:** Backend generates ephemeral WebRTC room tokens and facilitates SDP offer/answer exchange via `/ws` WebSocket.
3. **Media Transport:** Parent and Child establish P2P media stream (or relay via Coturn TURN server if NAT traversal fails).
4. **Session Teardown:** Upon disconnect, backend records consumed duration, logs session in `audit_logs`, and notifies child device.

## 6. Features Requiring Backend Architecture Decisions

The following features require specific architectural patterns during Phase 1:
1. **Media Storage Lifecycle & Auto-Purge:**
   - `cloud_data_retention_control` & `clear_all_family_data` require a scheduled cron worker (BullMQ) that runs daily at midnight, queries `media_assets` where `created_at < NOW() - INTERVAL 'X days'`, deletes objects from S3, and removes metadata rows.
2. **Realtime RTC Provider Abstraction Layer (PAL):**
   - `live_screen_mirror` & `live_camera_stream` must not hardcode Agora or LiveKit. A provider adapter pattern (`IRtcProvider`) must decouple token generation and signaling.
3. **Asynchronous Command Queue with TTL:**
   - `asynchronous_command_task_queue_progress` requires handling offline child devices. Commands in `device_commands` must support TTL (e.g. 24h expiration), state transitions (`PENDING`, `DISPATCHED`, `COMPLETED`, `FAILED`, `EXPIRED`), and retry logic.
4. **Telemetry Ingestion & Time-Series Partitioning:**
   - `location_telemetry` and `notification_logs` generate high-write volume. PostgreSQL 16 monthly table partitioning + TimescaleDB/PostGIS GIST indexing must be configured in initial migrations.

## 7. Recommended Backend Implementation Sequence

The 85 Backend-Required and 82 Backend-Partial features are mapped to the 6 execution phases from `PLAN.md`:

1. **Phase 1: Foundation, Database & Core Auth (P0):** Fastify, Drizzle ORM, PostgreSQL 16 + PostGIS, Redis 7, JWT auth, `users`, `devices`, `device_pairings`, `system_features`.
2. **Phase 2: Dynamic Policy & Rule Management (P0/P1):** `device_policies` JSONB engine, versioned sync API (`GET /policy`), `app_blocking`, `screen_time_schedules`, `web_filter_vpn`, plan entitlement checking.
3. **Phase 3: Realtime Engine, Command Queue & RTC (P1):** WebSocket `/ws` hub, `device_commands` state machine, WebRTC signaling layer, remote instant lock, alarm siren.
4. **Phase 4: Telemetry Ingestion, Media Storage & Geofencing (P1):** PostGIS geofence evaluation, S3 presigned upload pipeline, `media_assets`, `location_telemetry`, `notification_logs` keyword safety scanner.
5. **Phase 5: Subscriptions, Addons & Analytics (P2):** Stripe/Google Play webhooks, `plans`, `plan_features`, `quota_vouchers`, weekly aggregation cron jobs.
6. **Phase 6: Super Admin Panel & Hardening (P2/P3):** Global feature kill-switch dashboard, user/device management UI, audit trail inspection.
