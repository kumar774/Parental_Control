# Child Android App - Security Architecture & Hardware Hardening
## Enterprise Cryptographic Standards (Android 8.0 to Android 15, 16, 17+)

---

## 1. Security Architecture Principles
The Child App resides on an untrusted endpoint (the child's physical device) where the user may attempt to:
1. Uninstall, freeze, or force-stop the process.
2. Intercept or tamper with network traffic (MITM via Charles Proxy, Burp Suite, or custom CA certificates).
3. Spoof GPS coordinates or inject fake location data.
4. Tamper with local SQLite databases or settings.

To prevent this, the Child App adheres to a **Zero-Trust Hardened Cryptographic Foundation**.

---

## 2. Core Security Controls Specification

### A. Device-Bound Cryptographic Keys (Android KeyStore StrongBox / TEE)
* **Hardware Root of Trust:**
  * Upon initial pairing, the child device generates an asymmetric **ECC (Elliptic Curve Cryptography) P-256** key pair inside the **Android KeyStore**.
  * On devices supporting it (Pixel, Samsung, flagship Qualcomm/Tensor chips), keys are isolated inside **StrongBox Keymaster (Dedicated Hardware Security Module - HSM)** or **TEE (Trusted Execution Environment)**.
  * The private key **never leaves the secure enclave hardware** and cannot be extracted even with root or bootloader unlock.
* **Public Key Exchange:**
  * During pairing, the public key is transmitted to the Fastify backend via TLS 1.3 and bound to the `child_devices.device_key_fingerprint` record.

### B. Cryptographically Signed Commands (Anti-Replay & Anti-Tamper)
* **Command Verification:**
  * When a parent issues a high-privilege remote command (e.g. `LOCK_SCREEN`, `WIPE_DATA`, `TRIGGER_STREAM`), the backend signs the payload with a time-limited HMAC-SHA256 signature and nonce.
  * The child app verifies the signature and validates that:
    1. The timestamp is within a 30-second window (prevents replay attacks).
    2. The nonce has not been previously processed (stored in memory bloom filter).
    3. The payload signature matches the backend authority key.

### C. TLS 1.3 Transport Encryption & Certificate Pinning
* **In-Flight Data Protection:**
  * All REST API calls and WebSocket connections strictly enforce **TLS 1.3** using modern cipher suites (`TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`).
  * Plain HTTP (cleartext traffic) is permanently disabled in `AndroidManifest.xml` via `android:usesCleartextTraffic="false"`.
* **Network Security Configuration:**
  * Certificate pinning is enforced for the server domain. Custom user certificates added to Android's credential store (e.g. proxy certs) are explicitly ignored by OkHttp.

### D. Argon2id & Password Derivation
* **Local Master PIN Verification:**
  * When the parent enters the emergency master PIN directly on the child's screen, the PIN is verified using **Argon2id** (memory-hard password hashing).
  * Plaintext PINs are never stored in MMKV or SQLite. Only the salted Argon2id hash is stored locally.

### E. Multi-Factor Authentication (MFA) & Step-Up Auth
* Sensitive child actions (such as authorizing device unbinding, revoking Device Admin, or transferring profile) require step-up MFA verification via email OTP or TOTP Authenticator.

### F. Role-Based Access Control (RBAC) Enforcement
* Multi-tenant authorization boundary:
  * Super Admin -> Platform fleet monitoring & policy overrides.
  * Primary Parent (Owner) -> Full administrative control over child device rules.
  * Co-Parent / Guardian -> Read-only or restricted control based on permission matrix.
  * Child Device -> Telemetry producer and command consumer; cannot read parent logs or cross-tenant device records.

### G. Local Encrypted Storage (SQLCipher / EncryptedSharedPreferences)
* The local Room SQLite database is encrypted at rest using **256-bit AES-GCM (SQLCipher)**.
* Even if an attacker uses ADB backup or physical forensic tools, the database files (`location_cache.db`, `incident_logs.db`) remain encrypted.

### H. Audit Logging & Non-Repudiation
* Every security-sensitive event is logged with:
  * Timestamp (UTC ISO-8601)
  * Event Type (e.g. `TAMPER_ATTEMPT`, `PERMISSION_REVOKED`, `STREAM_STARTED`)
  * Cryptographic signature generated by the child device's KeyStore private key.

### I. Automated Security & Penetration Testing
* **CI/CD Security Gate:**
  * Static code analysis (SAST) with SonarQube & Android Lint.
  * Dependency vulnerability scanning with npm audit / Gradle dependency check.
  * Dynamic penetration testing (DAST) testing for SSL pinning bypass, root detection evasion, and accessibility abuse.
